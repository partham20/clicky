# Clicky for Windows

An AI cursor buddy for Windows. It looks at your screen when you press a hotkey, talks back, points and draws, teaches, dictates, and runs computer-use agents and MCP-connected apps.

## Layout

| Project | Target | Role |
|---|---|---|
| `src/Clicky.App` | `net10.0-windows10.0.19041.0`, WPF | Composition root: Generic Host, tray, windows |
| `src/Clicky.Core` | `net10.0` | Settings, coordinate mapping, buddy state, hotkey gesture engine, audio conversion and speech gate, OpenAI speech-to-text, sentence streaming and the speech pipeline, OpenAI text-to-speech, prompts, the action schema, the Claude backends and router, memory, Clickys (SQLite), and later the agent loop. No Windows APIs |
| `src/Clicky.Platform.Windows` | `net10.0-windows10.0.19041.0` | Single instance, start with Windows, per-monitor overlays, monitor and cursor info, keyboard hook, screen capture, microphone, Whisper, Credential Manager, speakers, Windows voices, call/share/Focus Assist detection, and later input, UIA |
| `tests/Clicky.Tests` | `net10.0` | xUnit |

Windows 10 2004 (build 19041) is the floor because overlays need `WDA_EXCLUDEFROMCAPTURE`.

## Data

Everything lives in `%AppData%\Clicky` (override with the `CLICKY_DATA_DIR` environment variable):

- `settings.json`: hand-editable (comments and trailing commas allowed). Edits apply live. A file that is corrupt at startup is moved to `settings.json.<timestamp>.bad` and defaults are written. An invalid edit while running is ignored and the last good settings stay active.
- `overlay.hideFloatingCursor` (also in the tray menu): the buddy stops following the pointer and docks to Home. `overlay.followSmoothingMs` (default 40, 0 to 300) sets how loosely it trails the pointer; 0 pins it.
- `hotkeys.bindings`: one entry per action, e.g. `{ "action": "Talk", "gesture": "Ctrl+Alt", "enabled": true }`. Also editable in Settings. A binding that can't be read is logged and skipped; the rest keep working.
- `capture`: `mode` (`MonitorUnderCursor`, `ForegroundWindow`, `AllMonitors`), `maxLongEdge` (1568), `maxPixels` (1150000), `includeCursor` (false).
- `voice`: `engine` (`Local` or `Cloud`), `language` (`en`, `hi`, … or `auto`), `localModel` (`large-v3-turbo-q5_0`, used on the GPU), `cpuModel` (`small.en-q5_1`), `useGpu` (true; applies on restart), `cloudModel` (`gpt-4o-mini-transcribe`), `inputDevice` (empty follows the Windows default), `minSpeechMs` (300), `maxRecordingSeconds` (120). Also in Settings › Voice.
- `debug.saveCaptures`: also write every screenshot to `debug\captures\yyyyMMdd-HHmmss.png`, with a red crosshair where the pointer maps to. Off by default; nothing else writes screenshots to disk.
- `speech`: `quietMode` (false; also in the tray menu), `engine` (`Windows` or `Cloud`), `windowsVoice` (empty uses the Windows default voice), `cloudModel` (`gpt-4o-mini-tts`), `cloudVoice` (`coral`), `rate` (1.0, 0.5 to 2), `volume` (1.0, on top of the Windows volume), `outputDevice` (empty follows the Windows default), `quietInCalls`, `quietWhenSharing`, `quietInFocusAssist` (all true), `ignoreMicApps` (apps that hold the mic without being in a call, e.g. `"NVIDIA Broadcast.exe"`). Also in Settings › Speech.
- `debug.saveAudio`: also write every Talk recording to `debug\audio\yyyyMMdd-HHmmss.wav` (16 kHz mono). Off by default; nothing else writes audio to disk.
- `claude`: `backend` (`Api` or `Subscription`), `routing` (`Auto`, `AlwaysFast`, `AlwaysDeep`), `apiFastModel` (`claude-haiku-5-5`), `apiDeepModel` (`claude-opus-5-5`), `subscriptionFastModel` (`haiku`), `subscriptionDeepModel` (`opus`), `fastEffort` (`Low`), `deepEffort` (`Medium`), `maxTurns` (40), `idleResetMinutes` (10), `cliPath` (empty finds `claude.exe`). Also in Settings › Claude. The Anthropic key is in Credential Manager as `Clicky/anthropic-api-key` (or `ANTHROPIC_API_KEY` for development).
- `skills\*.md` (and `skills\<name>\SKILL.md`): app guides sent with questions asked while that app is in front (see Walkthroughs below). The folder gets a README with the format on first run.
- `memory\PROFILE.md` and `memory\VOLATILE.md`: what Clicky remembers about you (see Memory below). `memory`: `enabled` (true), `autoUpdate` (true), `idleMinutes` (3). Also in Settings › Memory.
- Speech models live in `%LocalAppData%\Clicky\models` (not roaming), downloaded on first use and checked against their SHA-256.
- The OpenAI key for cloud speech-to-text is in Windows Credential Manager as `Clicky/openai-api-key` (Settings › Voice, or the `OPENAI_API_KEY` environment variable for development), never in settings.json.
- `updates`: `autoCheck` (true), `autoDownload` (true), `feedUrl` (empty means GitHub releases of this repository; another GitHub repo URL, an https URL or a local folder with `releases.win.json` also work), `prerelease` (false). Also in Settings > Updates and support.
- `bug-reports\clicky-bug-*.zip`: made by Report a bug; the newest 5 are kept.
- `dictation`: `maxMinutes` (30), `typeWhileSpeaking` (true, hands-free), `spokenCommands` (true), `learnCorrections` (true), `keepHistoryDays` (30), `cleanup` (`Auto`, `Always`, `Off`), `terminalApps`, `pasteApps`. Also in Settings › Dictation. `dictionary.json` is the personal dictionary and `dictation\` the transcript history (see Dictation below).
- `onboarding`: `completed` (false until the tour is finished or closed once), `tutorialVersion`. Onboarding opens at startup while `completed` is false, or when a newer tutorial ships.

Also in Settings › Agents. See Computer use below. Clicky's own browser profile is `%LocalAppData%\Clicky\browser`.

## Behaviour notes

- One instance per user per logon session (`Local\` mutex). A second launch asks the running copy to open Home (Settings with `--settings`) and exits with code 0.
- Start with Windows writes `HKCU\...\Run`. If you turn Clicky off in Task Manager's Startup tab, Clicky respects that and switches its own setting off. Under a Velopack install the entry points at the root launcher stub, so updates don't break it.
- The cursor buddy lives on one transparent overlay per monitor. The overlays are click-through, never take focus, stay out of Alt+Tab and the taskbar, and are excluded from screen capture. They are rebuilt when monitors are added, removed, moved or rescaled.
- While the pointer is still, the buddy costs a ~30 Hz cursor poll and nothing else. Per-frame work runs only while it is moving or animating a state.

## Hotkeys and capture (M2)

| Action | Default | Notes |
|---|---|---|
| Talk | Hold Ctrl+Alt | Buddy listens and a screenshot is taken while held |
| Type a question | Double-tap Ctrl | |
| Dictation | Hold Ctrl+Win | |
| Hands-free dictation | Double-tap Ctrl+Win | |
| Open Home | Ctrl+Alt+A | |
| Always-on voice | Triple-tap Ctrl | Off by default |

Talk, Open Home and both dictation gestures (M12) work; the others are logged until their milestones. Talk sends what you say and a screenshot to Claude and speaks the answer (M6).

Gesture text in settings: modifiers alone are a hold (`Ctrl+Alt`), modifiers plus a key are a press (`Ctrl+Alt+A`), and `double`/`triple` prefixes are taps (`double Ctrl`). `hold Ctrl+Space` holds a key. A modifier-only hold needs two modifiers, and a press needs a modifier unless the key is F13-F24, so a binding can't take over normal typing.

How it works: a `WH_KEYBOARD_LL` hook on its own thread feeds `GestureEngine` (Core, unit tested on a fake clock). The callback only translates the event and asks the engine; events leave through a channel, so nothing slow ever runs inside the hook.

- **Timing.** A modifier-only hold arms after 200 ms with exactly its modifiers down and no other key pressed. A tap is a press-and-release within 250 ms with nothing else in between; taps count up while each starts within 300 ms of the last release. Any other key cancels: Ctrl+Alt+A opens Home and never starts Talk, and Ctrl+C is never a tap.
- **Triple-tap latency.** When a chord has both a double and a triple binding, the double has to wait out the 300 ms window to rule out a third tap. With always-on voice off (the default), double-tap Ctrl fires the moment you release the second tap.
- **AltGr.** On layouts with AltGr, Windows sends a fake left Ctrl (scan code 0x21D) before right Alt. The engine ignores it, so AltGr is plain Alt to us and typing `@` or `€` never looks like Ctrl+Alt.
- **Start menu.** Releasing Win after Ctrl+Win would open Start. When a Win gesture of ours owns the release, the hook swallows the Win key-up and injects VK 0xFF (unassigned) down/up followed by the Win key-up in one `SendInput`, so the shell sees "another key was pressed" and stays closed. Win on its own and Win shortcuts like Win+D are left alone.
- **Injected input is ignored.** Keys from `SendInput` (remote tools, AutoHotkey, on-screen keyboards, our own mask key) never trigger or block a gesture.
- **Elevated windows (UIPI).** While an administrator window has focus, Windows sends its keystrokes to no lower-integrity hook, so hotkeys do nothing there. The log says so once per window. Key-ups can also go missing when focus moves to such a window or to the secure desktop. While a hold is active, the held keys are checked against `GetAsyncKeyState` every 100 ms, and again on every focus change, so a hold can't get stuck. Session lock/unlock resets everything.
- **Recording.** The shortcut box in Settings records through the same hook, which pauses all hotkeys and swallows keys only while a Clicky window has focus, so Win can be recorded without opening Start.

Capture uses Windows.Graphics.Capture from the 19041 projection (no extra packages): one session per screenshot, first frame only, then closed. The D3D device and codecs are created at startup off the UI thread; after that a monitor capture plus PNG encode takes about 120-150 ms.

- **Size caps.** Images are downscaled (Fant) to fit both `maxLongEdge` 1568 and `maxPixels` 1.15 MP, never upscaled. A 4K monitor becomes 1429x804.
- **Coordinates.** `ScreenshotGeometry` records the captured rectangle in physical pixels and the image size. `CoordinateMapper.ToScreenshot` and `ToPhysical` convert between them. A physical pixel survives the round trip exactly (tested for every pixel at 100-175% layouts with negative origins and odd sizes). An integer screenshot pixel maps to the centre of the screen area it was shrunk from.
- **Overlays.** The buddy's overlays use `WDA_EXCLUDEFROMCAPTURE`, so the buddy is never in a screenshot.
- **Border.** On Windows 11, Clicky asks for borderless capture, so no yellow frame flashes. Windows 10 always shows it briefly.
- **HDR.** Frames are BGRA8; on an HDR monitor Windows tone-maps them to SDR, which can look washed out. The log records the capture format.

## Voice input (M3)

Hold Talk, speak, release: the buddy listens (its disc follows your voice), thinks while the speech is transcribed, and shows what it heard in a bubble beside it.

- **Mic opens on key-down.** The gesture engine announces a hold as `Pending` the moment its keys are down, 200 ms before it arms, and the mic opens then, so the first word is never clipped. A Pending that never arms (Ctrl+Alt+A, a quick tap) closes the mic and throws the audio away. Between Talks the mic is closed, so the Windows mic-in-use icon only shows while you hold.
- **Capture.** WASAPI shared mode in the device's own mix format (NAudio 3 `WasapiRecorder`, 50 ms buffers), converted in managed code to 16 kHz mono with a band-limited resampler. Each Talk opens the endpoint fresh, so plugging in a headset applies to the next Talk.
- **Speech gate.** An energy gate measures the recording against its own noise floor, needs at least `minSpeechMs` of speech, and trims silence to 250 ms either side. Silence never reaches Whisper, which would turn it into "Thank you." Whisper's subtitle habits (`[BLANK_AUDIO]`, `(music)`, "Thanks for watching!") are removed; short fillers such as "Thank you." are only dropped when there was barely any speech.
- **Local engine.** Whisper.net (whisper.cpp) through Vulkan, on the first discrete GPU (on a laptop Vulkan lists the integrated one first), with flash attention: `large-v3-turbo-q5_0` takes about 0.55 s for a 1.5-6 s question on an RTX A1000. Without a usable GPU it runs `small.en-q5_1` on the CPU with the audio context cut to the clip, about 0.4-0.6 s on a 14-core i7. The model loads and warms up at startup; the very first run on a machine also compiles GPU pipelines, which can take 20-45 s once.
- **Cloud engine.** OpenAI's transcription endpoint, 16-bit WAV upload, 20 s timeout. The Claude API has no speech-to-text, so this is a second provider.
- **Problems.** Mic blocked in Windows privacy settings, no mic, a mic unplugged mid-sentence (what was heard is still transcribed), a model still downloading, or a bad API key: each shows in the bubble, as a tray notification (at most once per 10 minutes per message) and in the log.
- **Bluetooth headsets** switch to their hands-free profile while the mic is open, so their audio drops to call quality during Talk. That is Windows; the laptop's own mic avoids it.

## Voice output (M4)

Replies are spoken sentence by sentence as their text arrives: the buddy shows Speaking, its glow follows the voice, and the sentence being said is its caption. Press Talk while it speaks and it stops (barge-in). Settings › Speech has a Test voice button.

- **Streaming.** Text is cut into sentences as it streams in (`SentenceSplitter`): at ". ", "! ", "? " and line breaks, but not at "3.14", "v1.2", "docs.claude.com", "e.g.", "Dr.", initials or "1." list numbers. Markdown, links, code blocks, table pipes and emoji are stripped before speaking (`SpeakableText`). Each sentence is synthesized while the one before it plays and queued behind it with a 180 ms pause, so there are no gaps. The look-ahead stops at about two sentences, so barge-in wastes little.
- **Windows voices** (default): WinRT `SpeechSynthesizer` with the voices installed in Windows, 15-30 ms a sentence once loaded at startup. Windows does not offer its newer natural Narrator voices to apps, so on most PCs these are the classic voices (David, Zira, Mark, Heera, Ravi, …). **Cloud**: OpenAI `gpt-4o-mini-tts`, natural voices, using the same Credential Manager key as cloud speech-to-text; it sends the reply text to OpenAI. The Claude API has no text-to-speech.
- **Speaker.** WASAPI shared mode in the device's own format, tagged as speech, opened per reply so new headphones apply to the next one. Opening it takes 250 ms to 1 s on Realtek drivers, so it is opened when Talk starts and kept for 15 s if no reply comes. Measured on an i7-13800H laptop: first sound about 30 ms after the first sentence is complete (about 180 ms at the speaker), and barge-in silences the voice within 45-60 ms, with a 15 ms fade so it doesn't click. A device unplugged mid-reply ends that reply with one log line and shows it as text.
- **Staying quiet.** Before each reply Clicky checks, in about 10 ms, whether to stay quiet. If so, the reply shows as a card by the pointer with a Copy button. The card doesn't take focus, stays out of screenshots and screen shares, and goes away after 8-45 s depending on length (not while the mouse is over it). The reasons, each logged:
  - Quiet mode is on (tray menu or Settings).
  - The speakers are muted, at zero, or missing (always).
  - **A call.** Windows has no "in a call" API. Clicky reads the microphone-in-use list Windows keeps for its privacy icon: another app holding the mic open almost always means a call (Teams, Zoom, Meet in a browser, Discord and Slack keep it open for the whole call, even when muted). An app that holds the mic for other reasons can go in `speech.ignoreMicApps`.
  - **Screen sharing.** There is no API at all. Most shares happen during a call, which already counts. On top of that, the sharing toolbars of Teams, Zoom, Chrome/Edge ("… is sharing your screen"), Firefox and Slack are recognized by their window titles. Anything else goes undetected; Quiet mode is the manual switch.
  - **Focus Assist / Do not disturb, presentations, full-screen apps and games.** `SHQueryUserNotificationState` (documented) for presentation mode, full screen and quiet time, plus the shell's own Focus Assist state (undocumented WNF) and Windows 11's Do not disturb setting. Each check fails open, to speaking, if Windows changes underneath it.
- **Overlays are not full-screen windows.** The shell treats a topmost window the size of the monitor as a full-screen app, so before M4 the buddy's overlays switched on Windows' automatic Focus Assist and reported the user as busy to every app. They now carry the shell's `NonRudeHWND` opt-out.
- **settings.json** saved as "UTF-8 with BOM" (Notepad and PowerShell can do that) used to count as corrupt; it now loads.

## Claude backends and actions (M5)

Two backends behind `IClaudeBackend`, switchable live in Settings › Claude, both streaming the same events: spoken text as it arrives, then validated actions, then usage and the stop reason.

- **API key** (`AnthropicApiBackend`): the official Anthropic C# SDK, streaming, the screenshot inline as base64, every non-speech action as a strict tool, adaptive thinking with per-tier effort, prompt caching on the fixed system prompt and tools plus automatic caching of history, and the server's default refusal fallback.
- **Claude subscription** (`ClaudeCodeBackend`): Claude Code headless, `claude -p` with stream-json in and out, so there is no API bill. It runs with no tools, MCP servers, settings, CLAUDE.md, skills or hooks (`--safe-mode`), in an empty folder (`%LocalAppData%\Clicky\claude-code`), without saving the session, and without the API key variables so it uses the subscription. Starting it takes 2-3 s, so one process is kept per conversation: it starts when Talk is pressed (M6) and later turns reuse it; the router switches its model with a control message instead of a restart. Barge-in sends an interrupt and keeps the process warm. Claude Code takes no custom tools, so the model writes actions as `<action>{…}</action>` tags that go through the same validation.
- **Action schema**: `Clicky.Core/Actions/actions.schema.json` (say, point, highlight, draw, step, click, type, key, scroll, wait, ask_permission, done) is the single source: the API backend makes tools from it, the subscription prompt embeds it, and every action is validated against it and checked against the screenshot (up to 8 px past an edge is pulled in, further is dropped and logged). Speech is plain text rather than a `say` tool call so it streams straight into the sentence speaker; it still comes out as `say` actions in the finished reply.
- **Prompts** live as Markdown in `Clicky.Core/Prompts` (embedded). The system prompt never changes within a run, so it stays cached; memory is fixed per conversation.
- **Router**: rules, not a model call. Short questions go to the fast model; "explain", "why", "walk me through", "fix", writing, long questions and agent steps go deep. Defaults: Haiku 5.5 (low effort) and Opus 5.5 (medium) on the API, `haiku` and `opus` on the subscription.
- **History**: the last 40 turns, trimmed 10 at a time and with old screenshots dropped in batches (at most 6 kept), so the cached prefix only changes every few turns. A conversation idle for 10 minutes starts over.

## Talk end to end (M6)

Hold Ctrl+Alt, ask about what's on screen, let go: the buddy listens, thinks with your question as its caption, then answers out loud as the reply streams in, pointing at, boxing or drawing on what it talks about.

- **Key down** (before the hold even arms): stops Clicky if it is speaking or still answering, fades the marks from the last answer, reads memory and gets the backend ready. On the subscription backend that starts Claude Code, so its 2-3 s start-up is over by the time you finish speaking.
- **Armed**: the mic is already open; the screenshot is taken with the pointer position you had when you pressed, and the pointer's ink trail (M9) starts recording.
- **Release**: speech-to-text, then `TalkLoop` (Core) asks Claude with the transcript, the screenshot and where your pointer is on it. Text goes to the sentence speaker as it arrives; point, highlight, draw and step actions go to the overlays mapped through the screenshot's geometry; click, type and the other agent actions are left to the computer-use agent (M13), which takes over in the same reply when it is installed (`IComputerAgent`). The ink trail is painted onto the screenshot and described in the question when the pointer moved over it. A capture that fails or takes over 3 s doesn't stop the question; it goes without a screenshot (and without ink).
- **Memory**: memory is part of the system prompt, fixed for the conversation so the prompt cache keeps hitting, except that feedback ("you talk too much") updates it for the very next answer. Every exchange is queued for the memory updater; when a conversation is dropped (10 idle minutes, or tray › New conversation) memory gets its pass straight away.
- **Problems** (no API key, Claude Code missing, rate limits, network): the buddy shows the reason as its caption and a tray notification says it, at most once per 10 minutes. Whatever was said before a failure stays said.
- **Hidden floating cursor**: with the buddy docked, what it heard, "Listening…", "Thinking…", each spoken sentence and any problem show as a subtitle at the bottom of the monitor you're on. It never takes focus or clicks and stays out of screenshots.
- **Startup**: the capture device (D3D11) and Whisper's GPU runtime (Vulkan) start one after the other, after the UI is up, and never at the same time (`GpuInitGate`). On Optimus laptops starting both together crashed Clicky in D3D11CreateDevice about one start in six. A capture warm-up that fails for any other reason is logged and the first Talk creates what it needs.

## Point, highlight and draw (M7)

`IAnnotationRenderer.Show(action, capture.Geometry)` puts a point, highlight, draw or step action on the overlays in a hand-drawn marker style: a pointer flies from the buddy (or from the previous pointer) to its spot and rings it, boxes and shapes draw themselves in with a slight wobble and overshoot, and labels pop up beside them in a handwriting font. Marks hold for 8 s (pointer), 10 s (shapes) or 60 s (steps) after drawing, then fade; `AnnotationOptions.Hold` overrides that, and `DismissAll()` clears the screen for the next question. Only one pointer shows at a time and at most 12 marks.

- The wobble is pure geometry in `Clicky.Core/Annotations` (`RoughSketch`, seeded, so it is testable and steady while animating); the planner maps screenshot pixels to physical pixels and refuses off-screen coordinates; `AnnotationBoard` and `AnnotationTimeline` decide what animates when.
- Frames are rendered only while something flies, draws in or fades; a still mark costs nothing but a one-shot timer for its fade, and only monitors with ink on them are redrawn.
- The overlays stay visible while any mark is up, even with the floating cursor hidden.
- Tray › Drawing demo (preview) plays every kind of mark on the monitor under the pointer.

## Ink trail: spatial context (M9)

While Talk is held the user can circle, underline or rest the pointer on things. The trail is drawn on the overlays as they go (pink ink with a white edge, in the M7 marker style; each bit holds 1.6 s and then fades, and what is left fades together shortly after release), and is sent to Claude with the screenshot taken when Talk armed: painted onto a copy of the PNG, and described as gestures in the user's turn, e.g. `[While talking, the user moved their pointer to show you something; ... In order, they circled the area (412, 220) to (560, 301); then rested the pointer on (700, 140) for 1.1 s.]`. The system prompt tells the model that "this" or "here" usually means what was circled, underlined or rested on.

- The talk loop calls `IInkTrailService`: `Start()` when Talk arms, `Finish()` on release (or `Cancel()`), then `AttachAsync(screenshot, trail)` before sending; it returns the screenshot with `RequestScreenshot.Ink` set, or unchanged when the pointer barely moved over it.
- The pointer is polled at 125 Hz on its own thread (high-resolution waitable timer), not hooked: nothing is added to every mouse event, it works over elevated windows, and the low-level mouse hook stays with walkthroughs (M8).
- Gesture reading and the painter are pure code in `Clicky.Core/Ink` (`InkAnalyzer`, `InkPainter`), in screenshot pixels: loops are found where the path crosses itself (circling twice is one circle), straight unhurried sweeps or back-and-forth along a line are underlines, rests of 400 ms or more are pauses, quick straight flicks are moves, the rest are paths. Ink off the screenshot is dropped.
- `settings.ink`: `enabled`, `showTrail`, `drawOnScreenshot` (all on by default). With `debug.saveCaptures` on, the inked screenshot is saved next to the debug captures.
- Tray › Ink trail test (preview) runs the same steps for 5 s without the voice and shows what Claude would be told.

## Walkthroughs and app skills (M8)

When you ask how to do something, Claude answers one step at a time (a `step` action: number, estimated total, instruction, and where to act). `IWalkthroughs` (Clicky.Core/Walkthroughs) takes it from there: it draws the step, waits for you to do it, lets the app react, takes a new screenshot and asks Claude for the next step itself (a `[Walkthrough]` request on the deep model), up to 15 steps, until Claude says done.

- Done is a click within about 24 DIP of the spot (wider when the screenshot was downscaled), a click anywhere on the element there, or that element getting keyboard focus, being pressed or selected (so Tab + Space works too). Steps without a spot (press a key, type something) move on with Done on the card.
- Three clicks elsewhere, pressing some other button, or switching to another app (not Start or search) counts as going another way: Clicky takes a new look and Claude either moves on or helps you back, at most twice per step.
- The step card at the bottom of the screen shows the step and has Back, Skip, Done and Stop; it never takes focus and stays out of screenshots. Asking something mid-walkthrough pauses it; it carries on after the answer. A walkthrough with no progress for 15 minutes ends.
- The mouse hook (`WH_MOUSE_LL`, on a thread of its own that only queues button events) and the accessibility hooks (WinEvents + MSAA bounds, on a second thread) exist only while a walkthrough runs. A non-elevated Clicky can't see clicks in an elevated window (UIPI); Done on the card still works.
- `TalkLoop` passes every reply event to `IWalkthroughs.Observe(event, geometry)` and leaves step actions to it, and sends the app guides for the app in front with each question. `IWalkthroughTurns` runs the engine's own requests (`AssistantWalkthroughTurns` by default). Talk clears the screen when you start asking; the current step comes back after the answer.
- App skills: Markdown files in `%AppData%\Clicky\skills` with a front-matter header (`name`, `apps` = process names, `titles` = window-title fragments, `description`). The guides for the app in front go in `ClaudeRequest.Context` (`IAppSkills.ContextFor`), at most 3 per request and about 12,000 characters each, once per conversation and again after the file changes. Edits apply on the next question.
- Tray › Walkthrough demo (preview) runs a scripted four-step walkthrough of a practice window: mouse, keyboard, off-track, Back, Skip and Done, with no Claude involved.

## Text mode and documents (M10)

Double-tap Ctrl and a box opens by the pointer: type a question and press Enter (Shift+Enter for a new line, Esc stops an answer and then closes the box, double-tap Ctrl again closes it too). It asks through the same Talk loop as a spoken question (`TalkAnswerer`), as a typed question with the screenshot taken when the box opened, so the answer can point and draw like a spoken one. The answer streams into the box, with a Copy button; `settings.text.speakReplies` also reads it aloud. The box stays open for follow-ups in the same conversation (each follow-up takes a fresh screenshot), takes focus but stays out of the taskbar, Alt+Tab and screenshots, and closes by itself when you click away from it while it is still empty.

- **Files**: drop files on the box, or paste them (files copied in Explorer, or a snip as a picture). While you drag files anywhere, a "Drop here to ask Clicky" bubble appears just past the pointer, where the buddy is; dropping there opens the box with them (`settings.text.offerDropTarget`). PDFs are read page by page with PdfPig, Word and PowerPoint files straight from their XML (`.docx`, `.pptx`), and anything that decodes as text (code, logs, CSV, Markdown...) as text. Pictures (PNG, JPEG, GIF, WebP, BMP, TIFF) go as images, scaled to the screenshot caps. Old `.doc`/`.ppt`, spreadsheets, password-protected files and scanned PDFs without a text layer are refused with a reason on the chip. At most 10 documents and 5 pictures per question.
- **The open app's document**: when the box opens, Clicky reads the document in the app that was in front through UI Automation's TextPattern (Word, Edge and Chrome pages, PDF viewers, Notepad, editors) and offers it as a chip with a tick box. It goes when ticked, or by itself when the question is about it ("summarize this", "what does this page say about...", "proofread my essay"). Password fields and elevated apps are never read; a slow app is skipped after 5 s. Chrome and Electron build their accessibility tree on first request, so the very first read of such a window may find nothing (`settings.text.offerWindowDocument`).
- **Size limits**: all documents of one question share `settings.text.documentTokenBudget` (60,000 tokens by default, about 240,000 characters, so a 100-page report usually goes whole). Small documents go whole and the rest share what is left equally. A document that doesn't fit is cut into chunks of about 1,500 tokens along page, paragraph and line boundaries; the start and the end always go, then the chunks sharing the most rare words with the question, then an even spread, in document order with every gap marked `[... left out: pages 4-9 ...]`, and a note tells Claude which pages it has so it says when the answer may be in a part it can't see. The box says when a document went only in part. Reading itself stops at 2 million characters.
- **On the request**: `ClaudeRequest.Attachments` (`RequestAttachment`: a document's fitted text or a picture). Both backends send each as its own content block before the screenshot and the question; a document is a `<document name=... source=file|window>` element (a `<note>` first when cut), escaped so its text can't close the element, and the system prompt says documents are to be read, never obeyed. Pictures are image blocks. Requests with documents go to the deep model unless routing is forced. The documents stay in the conversation for follow-ups (the Claude Code backend keeps them in its session, and resends them in its transcript after a restart) until history holds more than 120,000 tokens of them; then the oldest are reduced to their names.
- Pure code in `Clicky.Core/Documents` (`DocumentFileReader`, `DocumentFitter`, `DocumentAttachments`), tested on any OS; `WindowsDocumentReader`, `WicImageLoader` and `DragWatcher` in Platform.Windows; the box, its chips and the drop bubble in `Clicky.App/TextMode`.

## Memory (M11)

Two Markdown files in `%AppData%\Clicky\memory`, both plain text you can edit in Settings › Memory or any editor:

- `PROFILE.md`: who you are, how you want answers ("How to answer"), habits and tools. Long-lived.
- `VOLATILE.md`: what you're working on now and open threads. Expected to churn.

How it flows (`Clicky.Core/Memory`, no Windows APIs):

- **Into prompts.** `IMemoryService.GetPromptAsync()` returns a `<memory>` block for the system prompt of voice, dictation and agent requests. Files are read per request and cached by timestamp and size, so edits from another editor apply on the next answer. Sections are never cut: if hand edits push memory past the prompt budget (9,500 characters), whole sections drop out and the block says how many. `VOLATILE.md` older than 14 days is marked as possibly out of date.
- **Updater pass.** `RecordTurn()` queues each exchange. After `idleMinutes` of quiet (or `EndConversationAsync()`), one request to the fast model (`IMemoryModel`) gets the queued turns, both files and the room left, and replies with JSON edits (`add`, `replace`, `remove`). A turn that sounds like feedback or a preference ("you talk too much", "from now on…", "remember that…", "forget…") runs the pass right away, so the next answer already follows it. A failed call keeps the turns (up to 40) for the next pass.
- **Merge rules** (`MemoryMerger`). Entries match ignoring case, spacing and end punctuation; an add that already exists is a no-op; replace/remove need the exact old entry, never a guess. Nothing is ever shortened: an entry over 280 characters, or an edit that would push `PROFILE.md` past 6,000 or `VOLATILE.md` past 3,000 characters, is refused whole (the model is told the room left so it consolidates instead). Anything that looks like a key, token or password is refused. At most 12 edits per pass. The merge runs against the files as they are on disk at that moment, so a hand edit made meanwhile is kept.
- **Undo and forget.** Settings › Memory can undo Clicky's last automatic change (this session, and only while the file hasn't changed since), forget one file or everything (resets to the empty template), and turn memory or automatic updates off.
- Writes are atomic (`.tmp` then move). Missing files are created from the templates.

Until a Claude backend registers `IMemoryModel`, memory is read into prompts but not updated automatically.

## Connectors (M16)

Settings › Connectors lets Claude use other apps through MCP servers, with the official C# MCP SDK (`ModelContextProtocol.Core`, client only). A **local program** is started by Clicky and spoken to over stdin/stdout (`npx`, `uvx`, `docker`, a full path). A **remote server** is reached over streamable HTTP, falling back to the older HTTP+SSE transport. Paste an `mcpServers` block from a README, or import `%AppData%\Claude\claude_desktop_config.json`.

- **Live.** Connectors live in `settings.connectors` and apply as soon as you save, hand edits included. Each enabled account is its own connection. A connection starts in the background at launch, lists its tools, follows `tools/list_changed`, and comes back on its own when the process exits or the network drops, after 1, 2, 5, 10, 30, then every 60 s. A server that never connects (wrong command) stops after 3 tries and shows why, with the last lines of its stderr. Retry tries again.
- **Tools for Claude.** `IConnectorTools` (Core) gives the backends and agent loop the tools of everything connected, named `<connector>__<tool>` (`<connector>-<account>__<tool>` when several accounts are on), always valid Messages API names of up to 64 characters. Each tool carries its JSON schema and the server's read-only/destructive hints. `NeedsConfirmation` is true for anything not declared read-only, and the permission gate runs on it. Calls never throw for a server problem; they come back as error results Claude can read. Results over 100,000 characters are cut. Tools can be switched off one by one.
- **Secrets.** API keys, secret environment values (`GITHUB_PERSONAL_ACCESS_TOKEN`, …) and OAuth tokens go into Credential Manager as `Clicky/mcp/<connector>/<account>/…`, never into settings.json. An imported server's `env` values are treated as secrets. One credential holds 1,280 characters and OAuth tokens are often longer, so values are split across `…#2`, `…#3` entries. Removing a connector or account deletes its entries.
- **OAuth.** MCP authorization: discovery from the server's 401 (protected-resource and authorization-server metadata), dynamic client registration, PKCE, and the RFC 8252 loopback redirect `http://127.0.0.1:<port>/callback` on a plain socket (no http.sys URL reservation, no firewall prompt). Background connects never open a browser. A server that needs a sign-in waits with a Sign in button, which opens the default browser and finishes when it redirects back (5-minute limit). Refresh tokens survive restarts, so you sign in once per account. Only `https:` authorization pages, or `http:` on loopback, are ever opened. For servers without dynamic registration, Advanced sign-in takes a client id and secret and a fixed redirect port.
- **Accounts.** A connector with credentials can have several accounts (Work, Personal), each with its own keys or sign-in. Tool descriptions say which account they act on.
- **Windows.** `npx` and other `.cmd` shims run through `cmd.exe` (the SDK does that). PATH is refreshed from the registry for each server, so Node or Python installed after Clicky started is found. Stdio servers get your profile folder as their working directory unless one is set. They are stopped (whole process tree) when Clicky quits; one Clicky crash can leave them running until they notice stdin closed.
- **Testing without Node.** `tests/Clicky.TestMcpServer` is a small stdio server (`echo`, `add`, `env`, `crash`, `grow`): command `dotnet`, arguments `<path>\Clicky.TestMcpServer.dll`.

## Dictation (M12)

Hold Ctrl+Win, speak, release: the text goes in at the caret of whatever app has focus. Double-tap Ctrl+Win for hands-free dictation, where each sentence is typed as soon as it is recognised, until you double-tap again (or hold Ctrl+Win). Start with "type a reply to this" and Claude reads the screen and writes the reply in your voice instead.

- **Chunked, so long sessions never drop.** Dictation audio streams through `DictationSegmenter` and is never kept whole: it is cut at the pauses between sentences (600 ms after 4 s of chunk, 1.2 s after any speech, a forced cut at the quietest moment before 25 s) and each chunk is transcribed while you keep talking, so release-to-text is only the last chunk (the rest is done already) and memory stays flat over 10+ minutes. Long silence is dropped as it arrives. One chunk that fails to transcribe doesn't lose the others, and a mic that dies mid-sentence keeps everything said before it. `dictation.maxMinutes` (30) stops a forgotten hands-free session.
- **History.** Every piece is appended to `dictation\yyyy-MM-dd.txt` the moment it is transcribed: text only, never audio. Kept `dictation.keepHistoryDays` (30; 0 keeps none).
- **Cleanup.** Spoken "new line" and "new paragraph" become line breaks when said as their own phrase ("a new line of products" is left alone). Dashes become commas. With an API key the fast model then fixes punctuation, capitals and small grammar slips (`dictation.cleanup`: `Auto` = API backend only, `Always`, `Off`); its answer is compared word by word with what you said and thrown away if it added, dropped or rewrote words, took longer than 4 s, or failed. On the subscription backend each call takes seconds, so `Auto` skips it there.
- **Personal dictionary** (`dictionary.json`, also in Settings › Dictation): words to spell your way, each with what speech-to-text writes instead (`{ "phrase": "Partha", "soundsLike": ["Parta"] }`). Phrases go into Whisper's prompt (OpenAI's too) so it prefers those spellings, and "sounds like" forms are replaced whole-word. Casing no sentence would produce ("GitHub", "WASAPI") is enforced without listing variants. When you fix a word by hand within about 20 s of it being typed, Clicky reads the field back (UI Automation), finds the one-to-three-word fix inside the inserted text, and learns it; rewrites, deletions, new typing after it and punctuation changes are not learned.
- **Insertion order.** (1) UI Automation `ValuePattern` for native Win32, WinForms and WPF edit boxes whose caret it can read (EM_GETSEL or TextPattern); the caret is put back after the text. Not for rich edits, passwords, or Chrome/Electron, where setting the value would bypass the page's editor. (2) Unicode keystrokes (`KEYEVENTF_UNICODE`), so the keyboard layout doesn't matter and nothing is a shortcut; it waits for the gesture's own keys to come up first. (3) The clipboard: for text with line breaks (so Enter never sends a Slack or Teams message), over 400 characters, apps in `dictation.pasteApps`, Windows 11 Notepad (it turns fast keystrokes into "ppppppppad"), and any app seen mangling typed text. The text is offered with delayed rendering and kept out of clipboard history and cloud clipboard; your clipboard is put back only after the app has actually read the text, so a slow app never pastes your old clipboard instead. An app that never reads it within 3 s leaves the text on the clipboard and you're told to press Ctrl+V.
- **Terminals.** Windows Terminal, the console, mintty, PuTTY, Alacritty, WezTerm, ConEmu, Tabby, Hyper and xterm.js terminals (VS Code's) get every line break turned into a space, so dictation can never run a command. `dictation.terminalApps` adds more by exe name. Terminal pastes use Shift+Insert.
- **Can't type there.** Administrator windows refuse input from a normal process (UIPI), so the text goes on the clipboard and the buddy says to press Ctrl+V. With nothing focused (desktop, taskbar), or when a hold is interrupted by another key, the text shows in a card with a Copy button instead of being typed into the wrong place. It is in the history either way.
- **Timing** on the i7-13800H / RTX A1000: a sentence chunk takes 0.9 s on the GPU once warm, so in hands-free mode text appears about 1.5 s after you pause, and release-to-text after a hold is under 1 s however long you spoke.

## Onboarding and Settings (M18)

**Onboarding** opens at the first start (and from the tray's Take the tour, or Settings › General). It is one window, about two minutes, every step skippable:

1. Welcome, with the main shortcuts (read from `hotkeys`, so it matches after rebinding).
2. Connect Claude: subscription (Claude Code) or API key, the backend's own check, and **Try it**, a real round trip on the fast model.
3. Microphone: the Settings › Voice section, so the Whisper download progress shows while you read on.
4. Practice, each completed by the real feature working, not by a click: **Say hello** (any Talk answer), **Watch it draw** ("point at the blue star": the answer put a mark on screen), **Circle something** (the Talk's ink trail reads as a circle, `InkAnalyzer`), **Dictate** (text arrives in the practice box). A failed answer shows Claude's reason in place.
5. Finish: shortcuts again and Start with Windows (on by default).

Finishing or closing marks `onboarding.completed`. The flow is `OnboardingFlow` in Core (unit tested); the window listens to `TalkAnswerer.Answered`.

**Settings** is a sidebar of pages: General (start with Windows, the tour, what screenshots contain, log level, debug saves), Cursor and character (follow or dock, follow smoothing, pointing while you talk), Shortcuts, Voice (input and speech), Typed questions and documents, Claude, Dictation and dictionary, Memory, Connectors, Agents (computer use; Clickys and routines can add sections), Suggestions (reserved for M17; it appears when a section is added), Updates and support. Pages are built when first opened and kept while the window is open. A module adds its settings with one line in DI, `services.AddSettingsSection<MyView>(SettingsPages.Agents)`; the view writes to `ISettingsStore` and follows `Changed` between Loaded and Unloaded like the others.

## Install, updates and bug reports (M18)

**Install.** `ClickyApp-win-Setup.exe` (Velopack) installs per user to `%LocalAppData%\ClickyApp` with no admin prompt and no .NET install (the build is self-contained, about 92 MB), adds Start menu and desktop shortcuts and an Apps & features entry, and starts Clicky. The pack id is `ClickyApp`, not `Clicky`, because Setup empties its install folder and `%LocalAppData%\Clicky` holds the speech models. The pack id must never change, or installed copies stop updating. The installer is not code-signed yet, so SmartScreen warns on first run.

**Updates.** A minute after startup and then every 6 hours the installed app asks GitHub releases for a newer version and downloads it in the background (deltas when the previous release is on the feed). It never restarts on its own: the tray menu gets **Update to x.y.z and restart** (and a notification says so once), and Settings > Updates and support has the same button plus Check for updates. Clicking it hands over to Velopack's updater, Clicky exits normally, the updater swaps `current\` and starts the new version. An update left waiting installs at the next start anyway. A development build (run from `bin\`) shows its version and skips all of this. Velopack's own log is `%LocalAppData%\Velopack\velopack_ClickyApp.log`.

**Start with Windows** points the Run entry at the stable stub `%LocalAppData%\ClickyApp\Clicky.exe`, never at `current\`, so it survives updates. Uninstall removes the Run entry. Uninstall keeps settings, memory and speech models (`%AppData%\Clicky`, `%LocalAppData%\Clicky`); delete those folders to remove everything.

**Releasing.** Push a tag (`git tag v0.2.0; git push origin v0.2.0`) or run the Release workflow by hand with a version. It tests, downloads the previous release for a delta, runs `build\pack.ps1`, and publishes a GitHub release with the Setup, full and delta packages and `releases.win.json`. Versions with a suffix (`0.3.0-beta.1`) or the pre-release box go out as pre-releases, which installed copies skip unless `updates.prerelease` is on. To try a release locally first: pack two versions into one folder, install the older Setup, set `updates.feedUrl` to that folder.

**Report a bug** (tray menu, or Settings > Updates and support): describe what happened, and Clicky writes `bug-reports\clicky-bug-<time>.zip` with `report.md` (the description plus version, Windows build, CPU, memory, monitors and DPI, language, voice and speech engines, update state), the last 7 days of logs (newest first, 30 MB cap, an oversized file keeps its end), `settings.json` and Velopack's log. Keys and tokens and the Windows user name in paths are removed from everything (`SecretRedactor`). Memory, screenshots and recordings are never included. Clicky sends nothing itself: Open GitHub issue opens a new issue with the description and system info filled in and shows the zip in Explorer to drag in.

**Separate instances.** A copy started with `CLICKY_DATA_DIR` set is its own single instance, so a test or dev build can run beside the installed one. Both still share the one `Clicky` Run entry.

## Clickys and Home (M14)

Home (Ctrl+Alt+A, the tray menu, or launching Clicky again) has the docked buddy and your Clickys on the left, the selected Clicky's chat in the middle, and Preview, Activity and History on the right.

- A Clicky is a persistent helper: a name, a colour, instructions sent with every task, notes it keeps in mind, and a files folder (`Files`, or drop files on the chat). Small text files in the folder (16 KB each, 48 KB in all) go with every task; the rest are listed by name. Templates in New Clicky give a starting point.
- Writing in its chat starts a run. Each run gets the Clicky's instructions, notes, files, what Clicky remembers about you (M11) and the last 20 exchanges of its chat, and goes to the deep model on the active backend. Replies are written to be read, in Markdown, not spoken. One run per Clicky at a time (later ones queue), and only one run at a time may use the computer.
- Runs can be paused (they hold at the next step boundary), resumed and stopped from the bar above the composer. A stopped run keeps what it said so far. A run cut off by quitting Clicky shows as Interrupted; History's `Ask again` reruns any finished task.
- A reply lands in the chat as unread (badge in the list) and, if you're not looking at that Clicky, as a Windows notification. Nothing is spoken.
- Preview renders the selected reply's Markdown in WebView2, or the HTML document it contains (a reply with an ```` ```html ```` block). Previews run with scripts off, a Content-Security-Policy, and every network request refused; links open in your browser. Without the WebView2 Runtime the preview falls back to plain text. `Save to files` writes the reply (`.md`, or `.html` for a document) into the Clicky's folder.
- Activity is the run's step log (requests, what it said, actions, refusals, pauses); History lists runs with status, trigger, duration, steps, tokens and cost.
- `Can see the screen and use the computer` lets a Clicky's runs take a screenshot and act through the computer-use agent (M13). Unattended runs never get a countdown or card. Turning the switch on is the permission for ordinary clicks, typing and connector tools; anything that sends, deletes, buys or can't be undone, and moving the real mouse, is refused (nobody is there to confirm it) and the Clicky says so.
- Schema changes run as numbered migrations (`PRAGMA user_version`); an existing database is copied to `clickys.db.v<N>.bak` before an upgrade, a damaged one is moved to `clickys.db.corrupt-<time>` and a fresh one started, and one written by a newer Clicky is left untouched with an error in Home.
- For code: `ClickyService` (in `Clicky.Core.Clickys`) is the API. `CreateAsync`, `UpdateAsync`, `DeleteAsync`, `ListAsync`; `SendAsync(clickyId, text)` for chat; `RunAsync(clickyId, ClickyRunRequest, ct)` runs a task and waits for its `ClickyRunOutcome` (routines use this; it throws `ClaudeBackendException` on backend failure); `Pause`, `Resume`, `Cancel`, `RetryAsync`; `Changed` and `RunFinished` events. Computer use plugs in as an `IClickyActor`.

## Routines (M15)

"Do this every morning" makes a routine: a prompt a Clicky runs on a schedule while Clicky is open. Ask for one in Talk or text mode, or add it in Settings › Agents (Home › Routines opens it), which also has Run now, Pause, History and Delete.

- **From a conversation.** Claude answers with the `routine` action (name, prompt, schedule; in the shared action schema, so both backends have it) and says what it is setting up. After the answer, the agent card asks "Save the routine …?" with the schedule, next run and prompt: **Save routine** or **Not now**, never Always. Proposals are asked one at a time and the card stays up while you carry on talking. On the API backend the answer goes back to Claude as the tool result if you answer before your next question. Routines made this way belong to no Clicky, so their result arrives as a Windows notification (and in History).
- **In a Clicky's chat.** Each Clicky run is offered `RoutineTools` for its own routines (`create_routine`, `list_routines`, `pause_routine`, `run_routine_now`, `delete_routine`; it can't see other Clickys' routines). ClickyService answers them between replies, within the Clicky's step cap. Creating (also via the `routine` action) and deleting ask on the same agent card: Save routine / Delete routine or Not now. A routine run is unattended: it is offered only list and pause, and creating, deleting or running routines is refused.

- **Schedules** (local wall-clock time, `RoutineSchedule`): once; daily on chosen days (every day, weekdays, …); every N minutes or hours, optionally between two times of day and on chosen days; monthly (31 = last day); a five-field cron expression; when Clicky starts (a minute after launch, so after sign-in when Clicky starts with Windows). Minimum gap 5 minutes. A time skipped by the spring DST change runs at the first minute after it; a time repeated in autumn runs once.
- **One timer.** `RoutineEngine` arms a single timer for the next due run, capped at 15 minutes, and otherwise waits on the network, sleep and clock events; nothing polls. The cap matters: .NET timers don't count time asleep, so a timer that comes back overdue is taken as a wake-up even when Windows' wake notice never arrives (Modern Standby).
- **Missed runs.** Runs missed while the PC slept, was off or Clicky was closed are caught up **once** (the latest one) if it was due within `catchUpHours`; older ones are recorded as skipped. A due run waits for the network (Windows' own connectivity check, with domain networks counted as online because corporate proxies often block its probe), 30 s after waking for Wi-Fi and VPN to come back, the end of a call, screen share or presentation (`holdDuringCalls`; Focus Assist alone doesn't hold anything since nothing is spoken), and a free slot (`maxConcurrentRuns`). An accepted run survives a restart.
- **Failures.** Three failed runs in a row pause the routine with the reason shown in the list and a Windows notification. A run cut short by sleep, Clicky quitting, or losing the network is retried rather than counted; one that runs past `runTimeoutMinutes` is stopped and counts.
- **Results** land in the Clicky's chat with an unread badge and are never spoken (`ClickyServiceRunner` over M14's `ClickyService.RunAsync`). A routine with no Clicky chosen (e.g. made by Talk) is answered by `AssistantClickyRunner`: Claude in a conversation of its own (never the Talk conversation, never recorded to memory), with the answer kept in the routine's History and shown as a notification. A routine whose Clicky was deleted fails with that reason and pauses after three tries.

## Computer use (M13)

Ask Clicky to do something ("rename this file to notes", "open my GitHub notifications", "turn on dark mode") and it does it: it acts, takes a fresh screenshot, sends Claude what happened and keeps going until the task is done, you press Stop, or `agent.maxSteps` (25) runs out. It works on both backends.

- **The agent card** sits in a bottom corner of the monitor being worked on. It shows the step, a Stop button, the "About to…" countdown and permission questions. It never takes focus (typing still goes to your app), is left out of screenshots, and moves to the other corner when a click would land on it.
- **Permission.** The first action in a conversation asks: Allow once, Always for this conversation, or Not now. Several actions in one step are asked about together. Anything that sends, posts, deletes, buys, pays, books, merges or deploys (by the control's name, risky shortcuts like Ctrl+Enter, or Enter in Teams, Slack, WhatsApp, Outlook and similar apps) asks every time and never offers Always. Connector tools not declared read-only ask too; read-only ones never do. Claude can also ask first (`ask_permission`), and a yes covers its next step. With Always, each new run counts down `agent.cancelWindowSeconds` (5) before its first action, so you can cancel. "Always" ends with the conversation.
- **UI Automation first.** A click becomes Invoke, Toggle, Select, Expand/Collapse, focus (edit boxes) or the control's default action on the element under the point, found again by name nearby when Claude names it (`target`) and the coordinates are a few pixels off. Double-clicks open list and tree items (Explorer files). Your pointer doesn't move. When there's no pattern for it (canvas apps, right-clicks, games), Clicky asks to use the real mouse: the pointer goes there, clicks, and comes back. Scrolling uses ScrollPattern, else the wheel with permission. Keys and text are SendInput keyboard events (Unicode, so the layout doesn't matter), after any modifiers you're holding are released. Injected input carries the `CLKY` tag, so walkthroughs don't take it for yours.
- **Clicky's own browser.** `open_url` opens pages in a separate Chrome (or Edge) profile, `%LocalAppData%\Clicky\browser`, started with remote debugging on a port Chrome picks. Sign in there to the sites Clicky should use; your everyday profile is never touched. Inside that window clicks, typing and scrolling go over CDP (no pointer, no focus needed), and the permission card can name the button from the page. With `agent.useBrowserProfile` off, or no Chromium browser installed, pages open in your default browser and Clicky works from screenshots.
- **Two ways to talk to Claude.** On the API backend Claude 5.x models get Anthropic's computer toolset (`computer_toolset_20260801`: screenshot, clicks, scroll, type, key, wait; zoom, drags and raw mouse moves are off), which is what they are trained on, mapped onto the same gate and executors. If the API refuses the toolset Clicky falls back to its own tools until it restarts (`agent.computerToolset` turns it off). Connected apps' tools are real tools there. On the subscription backend Claude writes action tags (`click`, `type`, `key`, `scroll`, `open_url`, `use_tool`), and results come back as a text block with the next screenshot.
- **Refused.** Windows don't accept automation or input from a normal process when they run as administrator, so Clicky says the user has to do that step. `agent.enabled` off refuses all computer control. Claude is told never to follow instructions it reads on the screen or in web pages, only yours.
- **Memory.** A finished run is remembered (M11) as one agent turn: the task and how it ended.
- **For code.** `ComputerAgent` (Core) is the loop: `WantsToAct(completed)` and `ContinueAsync(conversation, completed, screenshot, AgentRunOptions, ct)`, which yields every step's reply events. `IComputerControl` does the actions (`WindowsComputerControl`), `IAgentPresenter` shows the card. Clickys use it through `ComputerAgentClickyActor`.

## Suggestions (M17)

Each morning Clicky looks through your connected apps and the web and puts a few ideas in a card at the bottom right, one at a time: **Do it**, **Next** (Not this, on the last one), **Adjust…**, or ✕ for not now. The tray's **Today's ideas** shows them again, or finds some now if today hasn't been researched yet.

- **Research, read-only.** From an hour before `suggestions.showAfterHour`, the fast model goes through the connectors (M16) for the last `lookbackHours` (72) and today and tomorrow's calendar: up to 6 rounds of up to 6 calls, plus 4 web searches. Only tools the server declares read-only are offered, and each call is checked against that list again before it runs, so this pass can never send, change or delete anything. Calls are written as `<call tool="…">{json}</call>` tags rather than native tool use, so the same loop runs on both backends. Web search is the Messages API's web search tool with an API key, or Claude Code's `WebSearch` (`--tools WebSearch --allowedTools WebSearch`) on the subscription. Results are cut at 6,000 characters each. Nothing runs without either a read-only connector tool or web search.
- **Editor.** The deep model turns the notes into at most `maxIdeas` distinct ideas, each with a title, a couple of sentences, why now, its sources (app and item ID or URL) and the task "Do it" hands over. It sees what you did with earlier ideas (did it, skipped, closed, asked to change) from the last 45 days, and the ideas of the last `noRepeatDays`. `RepeatFilter` then drops anything about the same item, with the same topic, or sharing most meaningful words with an idea from those days, without trusting the model to have listened.
- **The card.** It appears from `showAfterHour` until `lastHour`, once you have used the keyboard or mouse in the last 2 minutes and are not in a call, sharing your screen, in Focus Assist or full screen, and not talking to Clicky. It never takes focus, stays out of screenshots and shares, and goes away after 20 minutes (not while the mouse is over it). **Do it** hands the task to Talk as a typed request, so the answer comes like any other, and the computer-use agent (M13) carries it out when it is installed; anything that sends or changes something is drafted for you to confirm. **Adjust…** asks what to change and the deep model rewrites that idea.
- **Back-off.** A morning whose card goes away with no reaction counts as ignored. After 3 ignored mornings in a row the card comes every 2nd day, then every 4th, then weekly; any reaction brings it back to daily. Research is skipped on the days in between.
- **Cost.** One research pass (a few fast requests) and one deep request a day; nothing on days with no card.
